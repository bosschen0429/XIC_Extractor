# Diagnostic Ledger And Rerun Policy

Doc placement: formal_repo_doc
Doc kind: report
Doc lifecycle: active
Repo owner: docs/diagnostic-ledger.md
Doc exit rule: Keep active while expensive RAW rerun memory is needed; retire only after durable diagnostic memory moves to a replacement canonical owner.

**Status:** maintained repo-local diagnostic memory
**Last updated:** 2026-10-26

This ledger records diagnostic conclusions that should survive branch and
worktree changes. Use it before rerunning expensive RAW validation or treating a
known target as a new blocker.

This file is not a replacement for task-specific validation notes. It is the
small durable index that tells future agents which prior conclusions are already
known, where the evidence lives, and when a rerun is justified.

This file is also not the live productization tier board. Product maturity tier,
active lane, current writer counts, promotion-packet status, and Backfill
authority scopes are owned by the productization status index
`docs/superpowers/validation/productization_status_index.tsv`, the authority
manifest
`docs/superpowers/productization/status/productization_authority_manifest.json`, and the
promotion contract `docs/agent/product-validation-contract.md`. When this ledger
cites a historical validation note, treat it as diagnostic/rerun memory unless
a current structured authority artifact still promotes the same claim. The
dated productization control-plane path is compatibility lookup only.

## Use Rules

- Read this ledger before investigating a previously seen target, family,
  failure mode, or validation gate.
- If this ledger already closes the diagnostic question, reuse the cited note or
  artifact instead of rerunning RAW.
- Treat programme-level `Frozen Inputs` as rerun memory when they point to a
  canonical owner or retained artifact. Reuse them until their checksum, public
  contract, owner, or implementation assumption materially changes; a new date
  alone is not invalidation. Keep programme status in its issue/map rather than
  copying it into this ledger.
- Rerun only when current code touched selection, boundary, identity,
  consolidation, integration, matrix delivery, or the cited artifacts are stale.
- Do not escalate from 8RAW to 85RAW when the 8RAW evidence is already `NO_GO`.
- Worktree `output/` paths are evidence references, not reusable inputs. Inputs
  that must survive worktrees belong under `local_validation_artifacts/`.
  Small diagnostic snapshots that must survive worktrees belong under
  `docs/superpowers/fixtures/` with a source note and hash.
- Keep an entry only while it still decides whether to rerun or which result to use,
  binds a current stable input, or supplies evidence for an open issue.
- Delete an entry once later evidence supersedes or disproves it, or its bound
  implementation or diagnostic tool is retired. Git retains the history; do
  not create a separate archive.
- Fold issue-named sections into dated entries under Known Diagnostic
  Conclusions when their conclusions still meet this rule.
- If a rerun changes a durable conclusion, update this ledger in the same PR.
- If a later status-index or authority-manifest entry changes maturity tier,
  writer scope, or product authority after a ledger entry was written, defer to
  the later productization authority and update this ledger only when the
  diagnostic/rerun conclusion itself changes.

### 2026-09-22 Composing A Partition In A Worker Costs More Than It Saves

- Composition is a pure function of the partition batch, its sample results,
  the alignment config and the known-ISTD reference: it opens no RAW and reads
  no acquisition cache. A spawned process reproduces a partition byte-identical
  to the parent's, and the result that has to come back is only 45,948 bytes
  because the worker writes the 115,074,919-byte partition itself. Reuse
  `offload-2-hashseed0/report.json` under
  `output/issue423-evidence-duplication-20260922/`.
- Offloading it still loses. With pipeline overlap on and the same source, the
  four compositions take 22.46 seconds in a worker against about 18.0 in the
  parent, plus 4.17 seconds decoding the inputs, and the parent ships
  173,946,280 request bytes it did not ship before. The parent is fast because
  it already holds that object graph; a worker rebuilds it from 42.0-49.4 MB
  per partition. Reuse `offload-run-3-overlap/`.
- There was also nothing to overlap with. In the retained overlap run every
  acquisition task finished by 35.02 seconds while composition ran to about 49,
  so composition never shared wall time with acquisition work. Check that a
  phase actually overlaps something before moving it off the parent.
- Raising the composition pool's `max_workers` does not create concurrency.
  Each composition dispatches its own single-item `run_windowed`, which sizes
  the executor to one; a pool set to three paid 151,150,806 bootstrap bytes and
  still reported one worker pid. True parallel composition needs non-blocking
  dispatch in the scheduler, not a wider pool. Reuse
  `offload-run-4-parallel/receipt.json`.
- Offloaded composition stops children flowing through the parent's
  `append_children`, which is where the child-level acceptance oracles observe
  them; that run's receipt reports `children: 0` while the batch still composed
  150. Any future attempt must read children back from the store instead.
- Sets reach the stream in hash order, so the same partition content serializes
  to different bytes in different processes: one run's spool digest was
  `15ced1b6...` and another's `570c8d06...` for identical input, matching only
  under a pinned `PYTHONHASHSEED`. Three `frozenset[str]` fields reach a
  composed child (`sample_universe`, `raw_sample_stems`,
  `selected_family_ids`). This cannot be fixed in the owner pickler: CPython
  bypasses both `dispatch_table` and `reducer_override` for exact `set` and
  `frozenset` instances. No consumer compares those digests across runs, so
  this constrains cross-process verification rather than product identity.
- Evidence is `diagnostic_only`. The store-side boundary that lets a partition
  be written elsewhere is kept at `df0f4f48`; the offload itself is reverted.

### 2026-09-22 Wall Noise Band And Three Falsified Evidence-Cost Claims

- Eight four-partition cache-only runs at `005fd18f` produce byte-identical
  deterministic output: 150 children, 82,336,732 request bytes and 103,023,549
  response bytes in every run. Wall ranges from 49.519 to 70.461 seconds. Three
  back-to-back uninstrumented `shared_pool_no_overlap_7f.py` runs alone give
  70.232, 50.848 and 49.519 seconds, a 20.713-second spread (42% of the
  minimum) with no source, input or configuration change. Treat any single-run
  wall comparison on this runner as uninformative; compare repeated runs or
  deterministic counters only. Earlier single-run wall differences in this
  ledger, such as 70.302 against 67.052 against 55.537 seconds, fall inside this
  band and must not be attributed to their code or configuration deltas. Reuse
  `baseline-1`, `baseline-2` and `baseline-3` under
  `output/issue423-evidence-duplication-20260922/`.
- Repeated evidence requests are not the cost. The 11,420 cache reads resolve to
  11,260 unique source-bound keys: 159 repeats inside one task and 1 across
  tasks. Reusing every exact-key repeat would save 23,802,912 of 711,432,392
  payload bytes (3.3%). All 6,934 XIC reads are unique. MS2 windows hold
  686,358,946 of those payload bytes across 4,486 parses over 4,326 unique
  windows, and each parse returns a mean 3.47 requested scans; unique
  (sample, scan) decodes are 11,956 of 15,567. A longer-lived sample evidence
  session, a sample-affinity scheduler and cross-task evidence caching are not
  justified by this data. Reuse `run-1/evidence-duplication-summary.json`.
- Worker parallelism is not the gap. The 680 tasks total 71.70 worker-seconds
  (initial mean 0.168s, recovery mean 0.043s), but workers are active for only
  11.60 seconds of a 57.60-second run; while active, mean concurrency is 6.18 of
  8. Worker-side optimisation is therefore bounded by roughly 20-24% of wall.
  Parent-side `owner_pickle_dumps`/`owner_pickle_loads` for all 680 tasks cost
  1.17 and 3.57 seconds, and each worker bootstrap is 50,528,292 bytes decoded
  in 0.45-0.67 seconds in parallel. Neither is the bottleneck.
- `pipeline_overlap` shows no measurable wall effect at fixed source. Overlap
  cuts idle gaps from 29.07 to 14.12 seconds and finishes all worker work 9.8
  seconds earlier, but the freed time moves into the tail (12.74 to 21.61
  seconds) because the four compositions stay a strict serial chain in the
  parent. The 57.60 against 56.63 second pair is inside the noise band above.
- Identity minting is not a duplication problem. Parent-side `_typed_digest` is
  115,992 calls over 86,519 unique results in 1.560 seconds;
  `_build_artifact_content_identity` is 53,054 calls over 42,024 unique results
  in 0.708 seconds across 173,058,870 bytes; `_canonical_basis_digest` is 1,144
  calls over 230 unique results in 0.385 seconds. Total 2.654 seconds;
  memoising every repeat recovers at most 0.851 seconds. Reuse
  `run-5-identity/identity.json`.
- Closing the eight process workers takes 6.636 and 6.686 seconds in two
  independent runs, unaffected by the overlap setting. It is the only cleanly
  isolated named block left in the parent-serial region; the remaining
  composition cost is distributed across `_build_production_composition_inputs`
  and streamed store writes, not concentrated in one owner.
- Method caveats for reuse. A 5ms parent stack sampler reported an effective
  18.8ms interval, and its proportions overstated CPU-bound hot spots about
  fourfold: it read identity minting as roughly 19% of the main thread against
  4.9% measured directly. Use its ordering, never its percentages. A timer
  placed on `execute_runtime_attempt` measures the whole pipeline, because the
  scheduler passes the pipeline itself as that call's `worker_batch_provider`.
  The sampler run's 70.461-second wall was initially read as sampler overhead;
  `baseline-1` reached 70.232 seconds with no sampler, so that attribution does
  not hold either.
- Evidence is `diagnostic_only`. No product code was modified to measure any of
  this; the probes are `evidence_duplication_423.py`, `evidence_timeline_423.py`,
  `evidence_timeline_423_overlap.py`, `evidence_tail_423.py` and
  `evidence_identity_423.py` under
  `output/issue422-bounded-worksets-20260921/fusion-ab/`, each a copy of the
